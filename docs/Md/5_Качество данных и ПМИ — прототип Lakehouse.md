## 1 Назначение документа

Документ задаёт правила контроля качества, методы испытаний и форму регистрации результатов. Покрыты все семь пунктов исходного тестового задания. Пункт 7, Superset, был опциональным в исходном задании и включён в объём сдачи прототипа как BI-07.

Сценарии сопоставлены с ТЗ-ХД-LAKEHOUSE-01. Паспорт фаз загрузки находится в РЗ-ХД-LAKEHOUSE-01. Порядок входа в инструменты и команды для ручного прогона приведены в РО-ХД-LAKEHOUSE-01.

## 2 Подход к контролю качества

Входные проверки выполняются над stage до записи Raw. Модельные проверки выполняются после подготовки Raw, Vault и снимков, до переключения опубликованных представлений. Все десять правил блокирующие для соответствующей фазы. Схема [«Контроль качества Lakehouse»](../diagrams/quality-gates.drawio) показывает точки контроля и ветви отказа.

Результаты считаются отдельно для объектов. Полное выполнение для корректного пакета даёт 33 входных и 59 модельных фактов. Эти числа относятся к одному полному прогону проверок, включая правила, которые на пустом входном наборе дают ноль нарушений.

## 4 Обработка результатов проверок

Ключ факта в iceberg.ops.dq_results состоит из run_id, phase, rule_id и object_name. Факт содержит batch_id, checked_at, expected_value, actual_value, violations и status. PASS означает равенство ожидаемого и фактического. Поле violations равно abs(actual_value − expected_value). Для сверки объёма это абсолютное расхождение счётчиков.

Если статус FAIL, оркестратор возвращает код 1 и прекращает выполнение последующих фаз. При входном отказе запись Raw не начинается. При модельном отказе снимки могут быть записаны, а пакет остаётся PENDING. Представления сохраняют предыдущий COMPLETE. Для invalid факт отклонения остаётся в dq_results, записи invalid в batches нет.

Ручная попытка использует новый run_id. Повтор SQL с тем же идентификатором, фазой и объектом сохраняет первую запись. Для анализа неполной попытки проверьте, какие фазы успели выполниться. Дашборд отображает сохранённые факты, в том числе ошибочный запуск.

```sql
SELECT run_id, batch_id, phase, rule_id, object_name,
       expected_value, actual_value, violations, status
FROM iceberg.ops.dq_results
WHERE run_id = 'manual-invalid'
ORDER BY phase, rule_id, object_name;
```

## 5 Программа и методика испытаний

### 5.1 Объект испытаний

Стенд Compose, восемь таблиц TPC-H SF 0.01, Raw, Data Vault 2.0, две витрины mart, журнал DQ и один дашборд Superset с двумя вкладками.

### 5.2 Цель испытаний

Подтвердить готовность стенда и сохранность на томах, типы и связи источника, версионирование, корректность витрин, воспроизводимость повтора, блокировку некорректного входа и работу дашборда.

### 5.3 Состав и условия испытаний

Подготовьте Docker Compose, Git, Bash, Make, Python 3.9+, локальный .env, свободные порты и отдельный Compose-проект с чистыми томами. Запускайте команды из корня клона. Для BI нужен браузер и профиль bi. Первый запуск требует образы и исходники. После подготовки стенда TPC-H доступен внутри Trino.

### 5.4 Методика испытаний

Пользуйтесь терминалом, Trino CLI, консолью MinIO и веб-интерфейсом Superset. Ручные фазы подробно перечислены в руководстве оператора. Повторяйте автоматический и ручной сценарии в разных чистых проектах. Сохраняйте вывод команды, запрос и результат с идентификатором сценария.

```bash
python3 scripts/lakehouse.py load --batch delta --stop-after-raw
make load BATCH=delta
make dq
python3 scripts/lakehouse.py input --batch invalid --run-id manual-invalid
echo "$?"
```

Проверку LOAD-05-2 начинайте до первой публикации delta. Можно объединить LOAD-05-1 и LOAD-05-2 в одном чистом прогоне, добавив остановку между повтором initial и завершением delta. Команды, для которых ожидается код 1, запускайте по одной. Make demo сам проверяет ожидаемые отказы и возвращает 0 при успешном сценарии.

После отрицательного прогона выполните запрос раздела 4, проверьте отсутствие invalid в iceberg.ops.batches и отсутствие пакета 3 в iceberg.raw.lineitem. Для сравнения опубликованных результатов используйте SELECT с ORDER BY 2,3 до и после отказа.

Для проверки без ограничения по периоду доля REG AIR = 4 302 / 8 616 ≈ 0,4993036. При активном периоде примените те же даты в SQL. В актуальном экспорте график доли отгрузок горизонтальный, значения подписаны в процентах, способы доставки различаются цветом.

```sql
SELECT ship_mode,
       CAST(sum(late_lines) AS double) / sum(shipped_lines) AS late_share
FROM iceberg.mart.shipping_by_mode
GROUP BY ship_mode
ORDER BY ship_mode;
```

### 5.5 Критерии оценки результатов

Сценарий пройден, если выполняются его критерии и приложены проверяемые свидетельства. Для отрицательного входа ожидаемое отклонение подтверждает работу DQ. Для сдачи комплекта требуется успешное покрытие всех семи пунктов, включая принятый в объём BI-07. Непроверенный сценарий отмечается отдельно от пройденного.
